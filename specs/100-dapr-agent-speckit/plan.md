# Implementation Plan: SpecKit Multi-Agent Workflow System

**Branch**: `100-dapr-agent-speckit` | **Date**: 2025-12-03 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/100-dapr-agent-speckit/spec.md`

## Summary

Build a multi-agent workflow system using the Dapr Agents Python SDK to automate the SpecKit feature development process. The system consists of 5 specialized agents (Orchestrator, Specifier, Planner, Task Generator, Implementer) that communicate via Dapr pub/sub and share state through Redis-backed Dapr state stores. The LLM Orchestrator pattern is used for intelligent routing between agents.

## Technical Context

**Language/Version**: Python 3.11
**Primary Dependencies**: dapr-agents, fastapi, uvicorn, anthropic, pydantic
**Storage**: Redis via Dapr state stores (workflowstatestore, agentregistrystore, memorystore)
**Testing**: pytest, pytest-asyncio
**Target Platform**: Kubernetes (Linux containers) with Dapr sidecar injection
**Project Type**: Multi-service microservices (5 agents in single container image)
**Performance Goals**: <60s spec generation, <10min end-to-end workflow, 10 concurrent workflows
**Constraints**: Memory <512Mi per agent, Dapr sidecar required
**Scale/Scope**: Single team (speckit), 5 agents, shared Redis backend

**Structure Decision**: Multi-service architecture with single container image. All agents share common code (config, models, health) but have separate agent implementations. The `AGENT_NAME` environment variable determines which agent to start, reducing image maintenance overhead.

## Implementation Phases

### Phase 1: Setup & Common Infrastructure
- Python project structure with pyproject.toml
- Environment configuration (Dapr component names, ports, team name)
- Shared Pydantic models (Workflow, Task, Artifact, WorkflowMessage)
- Health/readiness endpoints with Dapr connection check
- Base agent class with common Dapr configuration patterns

### Phase 2: Agent Implementations
- **Orchestrator**: LLMOrchestrator with AgentRunner, /run endpoint
- **Specifier**: DurableAgent with spec.md generation prompt
- **Planner**: DurableAgent with plan artifact generation prompts
- **Task Generator**: DurableAgent with tasks.md generation prompt
- **Implementer**: DurableAgent with task execution logic

### Phase 3: Integration & Testing
- Pytest fixtures for mock Dapr client
- Unit tests for models and prompts
- Integration tests for pub/sub message flow
- End-to-end workflow test

### Phase 4: Container & Deployment
- Dockerfile with multi-stage build
- CI/CD pipeline for image build and push
- Update CDK8s chart to use built image
- Verification in cluster

## Risk Mitigation

| Risk | Mitigation |
|------|------------|
| Dapr sidecar not ready at startup | Readiness probe checks Dapr metadata endpoint |
| LLM rate limits | Configurable retry with exponential backoff |
| Agent failures | Workflow state persisted, can resume from last checkpoint |
| Message ordering | CloudEvents with workflow_id for correlation |
